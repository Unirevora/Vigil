# 不眠手记 / Vigil — 重构 MVP 功能规格

> 文档状态：重构规划草案  
> 版本：MVP 1.0  
> 依据：原项目 `CHANGELOG.md`（v2.0.0 — v2.8.2，最新记录日期 2026-10-28）  
> 目标：完全重构原项目，以最小成本恢复稳定、可维护的核心使用闭环。  
> 说明：下文标注“建议”的内容属于新版本设计决策，并非原项目已确定的技术事实。

## 1. 项目目标

**产品定位：** 轻量、本地优先、以 Markdown 为主要写作格式的私人手记应用。

**MVP 核心闭环：**

创建手记 → 编辑内容 → 保存到本地 → 列表/搜索 → 阅读 → 再次编辑

同时保障数据可导出、可导入、可从旧项目迁移。

### 1.1 MVP 完成标准

- [ ] 用户能够创建、保存、查看、编辑、删除手记。
- [ ] 刷新页面或重启浏览器后，已保存手记不丢失。
- [ ] 用户能够按日期浏览手记，并按标题/正文关键词搜索。
- [ ] Markdown 正文在阅读模式下正确呈现。
- [ ] 用户能导出 JSON，并在新浏览器环境中导入还原。
- [ ] 能正确识别、校验并迁移原项目的可支持历史数据。
- [ ] 核心操作在移动端和桌面端正常运行。
- [ ] 核心数据操作与迁移逻辑具有自动化测试覆盖。

### 1.2 非目标

MVP **不追求**完整复刻原项目的动画、主题配置、节气内容、实时编辑器和所有自绘控件。任何新增功能不得以牺牲数据稳定性为代价。

## 2. P0 — 首版必须实现

### P0-01 手记管理

**功能范围**
- 创建手记。
- 修改已有手记。
- 保存手记（至少提供明确的保存操作和成功/失败反馈）。
- 删除手记，删除前二次确认。
- 手记最少包含：唯一 ID、标题、正文、手记日期、创建时间、更新时间。
- 建议允许空标题或空正文，但应明确定义展示规则，不因空值导致报错。

**验收标准**
- [ ] 创建手记后，刷新页面仍存在。
- [ ] 修改手记后，列表和阅读页都展示最新内容。
- [ ] 删除后，该条目不再出现在列表及搜索结果中。
- [ ] 连续点击保存或删除，不产生重复记录、重复执行和界面异常。

### P0-02 Markdown 写作

**功能范围**
- 使用可靠的纯文本编辑区输入 Markdown。
- 支持正常输入、换行、选区、复制、粘贴、撤销与重做。
- 标题、正文、日期可以编辑。
- 首版不实现 Obsidian 式 Token 级实时预览。
- 建议：编辑区与阅读渲染区分离，避免光标位置与 DOM 重建耦合。

**验收标准**
- [ ] 多行输入、退格、选择文本和中英文输入法正常。
- [ ] 保存的 Markdown 源文保持原样，不额外插入换行或标记。
- [ ] 较长正文仍能流畅编辑。
- [ ] 保存失败时提供明确提示，不能假装保存成功。

### P0-03 手记阅读

**功能范围**
- 独立阅读视图，显示标题、日期和 Markdown 正文。
- 渲染基础 Markdown：标题、段落、粗体、斜体、列表、引用、链接、代码、分隔线。
- 支持长正文滚动。
- 提供返回列表和编辑当前手记的入口。
- 渲染后的 HTML 必须做安全处理，不直接信任用户输入或导入内容。

**验收标准**
- [ ] Markdown 显示正确，原始 Markdown 文本未被修改。
- [ ] 长内容可完整滚动；短内容不出现严重空白或遮挡。
- [ ] 阅读和编辑切换不会意外丢失已经保存的数据。
- [ ] 恶意 HTML/脚本不能通过 Markdown 内容执行。

### P0-04 列表与搜索

**功能范围**
- “全部手记”列表展示标题、日期和简短摘要。
- 默认按手记日期倒序排列；日期相同按更新时间或稳定次序排序（建议）。
- 支持按标题和正文的关键词搜索。
- 点击列表项进入阅读页。
- 提供空列表和无搜索结果状态。

**验收标准**
- [ ] 列表数量与实际保存条目一致。
- [ ] 标题和正文搜索都能命中目标条目。
- [ ] 新建、修改、删除后列表及时更新。
- [ ] 无数据和无结果时有可理解的提示。

### P0-05 本地持久化

**功能范围**
- 采用本地优先的数据存储策略。
- 首版可沿用 `localStorage`；统一封装存取、解析、校验和错误处理。
- 定义应用数据 `schemaVersion`。
- 对不可用、损坏、超额的存储场景进行错误处理。
- 数据层与 UI 分离，方便未来替换为 IndexedDB 等存储实现。

**验收标准**
- [ ] 页面刷新和浏览器重启后可读取已保存数据。
- [ ] 读取损坏 JSON 时应用不会崩溃或覆盖原始数据。
- [ ] 存储失败时明确提示用户，保留当前编辑内容。
- [ ] 同一个数据操作不依赖具体 UI 组件。

### P0-06 JSON 导入与导出

**功能范围**
- 将当前手记数据导出为 JSON 文件。
- 从 JSON 文件导入手记。
- 导入前校验文件结构与数据类型。
- 导入时明确告知采用“替换”还是“合并”，首版建议仅支持**经确认后替换**，以减少 ID 冲突与去重复杂度。
- 建议：替换前先自动生成当前数据的可下载备份，或至少要求用户确认已备份。
- 导入失败时不改变现有数据。

**验收标准**
- [ ] 导出的文件能在空白环境中导入。
- [ ] 导入前后条目数、标题、正文和日期一致。
- [ ] 非法 JSON 或结构不匹配的文件会被拒绝且不破坏原有数据。
- [ ] 清楚提示覆盖风险；导入成功后页面状态同步更新。

### P0-07 旧数据迁移

**功能范围**
- 在开发前核查旧版实际 `localStorage` Key、数据字段和 `schema v2` 迁移逻辑。
- 定义旧数据 → 新数据的映射方案。
- 迁移应保留旧版信息；未在 MVP UI 中展示的字段，不应默认丢弃。
- 支持迁移前备份、可重复测试、失败回滚或停止迁移。
- 不得在未完成校验时主动删除原存储键。

**验收标准**
- [ ] 有代表性的旧数据样本及对应测试。
- [ ] 迁移前后条目数、正文、标题、日期一致。
- [ ] 空值、缺失字段、损坏记录有清晰策略。
- [ ] 迁移失败时旧数据保持可恢复。
- [ ] 已迁移数据再次启动不会重复迁移或重复生成条目。

**待核实（不能仅由更新日志确定）**
- 旧存储 Key 的完整名称。
- 条目、草稿、收藏的真实 JSON 结构。
- 旧导出格式及口令加密格式。
- 入口页是否依赖服务端鉴权或其他部署配置。
- 是否有旧版 ID 约束和日期格式差异。

### P0-08 最小界面与响应式

**一级入口建议**
1. 首页 — 最近手记、快速新建入口。
2. 全部手记 — 列表和搜索。
3. 写作/阅读 — 同一手记的编辑和查看（不是两个一级导航）。
4. 数据管理 — 导入、导出与迁移说明。

**视觉范围**
- 采用简洁纸张/墨色风格，保留产品辨识度。
- 先统一字体层级、间距、按钮状态、错误提示。
- 支持桌面与窄屏；建议优先验证 320px、390px、810px、1440px。
- 支持键盘基本交互、可见焦点、清晰的表单标签。
- 尊重 `prefers-reduced-motion`；首版动效保持最少。

**验收标准**
- [ ] 四个核心入口可以正常导航。
- [ ] 320px/390px 宽度下不出现关键控件无法操作或正文横向溢出。
- [ ] 对话框可通过按钮及 Esc 正常关闭（不阻止必需的确认操作）。
- [ ] 键盘可完成新建、保存、打开、返回等主要流程。

## 4. P2 — 首版明确不做

- Token 级实时 Markdown 源码/预览混排。
- 按行增量渲染、光标行源码显示与自绘编辑光标处理。
- 复杂沉浸模式、双栏实时预览、竖排文房与“观”面板。
- 节气旋转盘、拖拽预览、三候、月相、诗句联动。
- 纸张 3D 倾斜、散字聚拢/飞散、笔画重组、翻页动画。
- 画卷首页、照片叠层、自定义首页图片及装饰动画。
- 多语言动态热切换（英语、日语、繁体中文）。
- `Ctrl/⌘ + K` 命令面板。
- 自绘取色器、日期选择器、复杂下拉组件。
- 高级主题色自动反色及多套首页/导航版式。

**原则：** 不是永久删除，而是以“是否直接提升写作、检索、阅读、数据安全”为恢复依据。

## 5. 建议的数据结构（待与原项目核对）

下面是**新项目候选结构**，不是从更新日志推导出的旧版实际 schema。

```json
{
  "schemaVersion": 1,
  "entries": [
    {
      "id": "entry-unique-id",
      "title": "示例手记",
      "content": "# 今天",
      "date": "2026-10-28",
      "createdAt": "2026-10-28T08:00:00.000Z",
      "updatedAt": "2026-10-28T08:30:00.000Z",
      "legacy": {}
    }
  ],
  "exportedAt": "2026-10-28T09:00:00.000Z"
}
```

**设计建议**
- `id`：稳定的唯一标识，迁移时优先保留可用的旧 ID。
- `content`：仅存储 Markdown 源文，不持久化渲染后的 HTML。
- `date`：日记归属日期；与 `createdAt/updatedAt` 分开。
- `legacy`：临时保留旧版无法映射字段，待全面核对后决定如何规范化。
- `schemaVersion`：迁移时必须区分**新应用格式版本**与旧项目提及的 `localStorage schema v2`，不要误认为二者相同。

## 6. 建议的模块边界（非强制技术栈）

```text
src/
├─ app/                 # 应用初始化、导航与状态装配
├─ domain/
│  └─ entries/          # 条目模型、校验、查询、排序
├─ storage/
│  ├─ repository        # 本地读写接口
│  ├─ migrations        # 旧版与新版本数据迁移
│  └─ transfer          # JSON 导入、导出
├─ markdown/            # Markdown 安全渲染
├─ features/
│  ├─ home/             # 首页
│  ├─ entry-list/       # 列表、搜索
│  ├─ composer/         # 写作
│  ├─ reader/           # 阅读
│  └─ data-management/  # 数据管理
├─ ui/                  # 基础组件和样式变量
└─ tests/               # 数据、迁移、浏览器回归
```

**架构约束**
- 业务规则与 DOM 操作分离。
- 所有持久化入口经统一 Repository。
- Markdown 编辑源文与阅读渲染分离。
- UI 不直接依赖历史存储结构。
- 重要写操作必须返回成功/失败结果。
- 先保证测试和数据兼容，再考虑视觉增强。

## 8. P0 端到端验收场景

### 场景 1：第一次记录
1. 打开首页并新建手记。
2. 输入标题、日期和 Markdown 正文。
3. 保存并切换到阅读。
4. 刷新页面后重新打开该手记。
5. **预期：** 内容准确、可读、可再次编辑。

### 场景 2：搜索与维护
1. 创建至少 3 篇不同标题与内容的手记。
2. 搜索某一篇标题中的关键词。
3. 搜索另一篇正文中的关键词。
4. 修改其中一篇并再次搜索。
5. 删除其中一篇。
6. **预期：** 搜索及时更新，已删除条目不再出现。

### 场景 3：跨环境恢复
1. 创建多篇手记并导出 JSON。
2. 在新的空数据环境中导入 JSON。
3. 逐篇对照内容和日期。
4. 尝试导入损坏 JSON。
5. **预期：** 正确文件完整恢复；错误文件不影响已有数据。

### 场景 4：旧版升级
1. 准备旧版真实数据副本。
2. 运行迁移并检查完整性。
3. 再次启动新版本。
4. 人为制造不完整数据并重复测试。
5. **预期：** 正常数据无损、迁移幂等、异常情况下可恢复。

- [ ] 8 组 P0 功能通过验收。

- [ ] 旧版数据迁移使用真实样本验证通过。
- [ ] 导入/导出闭环验证通过。
- [ ] 桌面与手机主要操作无阻断。
- [ ] 数据层和浏览器核心流程测试通过。
